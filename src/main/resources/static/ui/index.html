What am I looking at? (open for a quick vocab primer)
agent A worker JVM that holds data partitions + a JVS SQL engine. Multiple agents = horizontally distributed cluster. Named agent-us, agent-eu, etc. in the demo.
driver Query planner + task dispatcher. You talk to it; it fans work to agents by capability match, then collects their rows.
broadcast table A table replicated in full at every agent — same rows, same schema on all of them. Use for small dimensions (country info, currency codes) so JOINs against them are cheap local lookups. Example: iso_currencies.
distributed table A table sharded across agents — different rows on each, addressed by a partition key. Scans fan-out; the driver merges results. Example: docs partitioned into us + eu.
partition One slice of a distributed table living on one agent. Partition key us → docs rows tagged "us" live on agent-us.
capability A string tag an agent advertises so the driver knows what it can do: jvssql, partition:docs:us, pipeline-node. Driver routes tasks by matching the required capability set.
task One unit of work handed from driver to agent — usually a partial SQL query over one partition. Three shapes: plain scan, shuffle-out, combine.
pipeline / node A DAG of processing nodes; each node is source → steps → sink(s). Nodes can be driver-local (Phase 1) or dispatched to agents (Phase 2).
source · step · sink A pipeline's building blocks. Source pulls rows in (ndjson-file, csv-file, sql, kvstore, lucene index, nats, kafka, ...); steps transform (filter, project, groovy-map, to-typed); sinks write rows out (memory-table, ndjson-file, kvstore, lucene index, nats subject, kafka topic).
reduce Group-by + aggregation on a node — COUNT, SUM, AVG, MIN, MAX, DISTINCT_COUNT, FIRST, LAST, COLLECT. Fires between steps and sinks.

Add distributed table (runtime registration)

Driver-side metadata only

Agents must already hold this table's data AND advertise each partition's required capability. If they don't, queries against this table will fail with "no live agent has capabilities…". In-memory only — lost on driver restart; use YAML config for prod.

Auto-derives capabilities as [jvssql, partition:<table>:<key>]. For custom capabilities, use the API directly (see docs).

Add broadcast table (runtime registration)

Name registration only

Registers the broadcast NAME with the driver's planner so JOINs to it are allowed. Every agent must independently pre-load the broadcast data via its own hitorro.mesh.agent.broadcast-tables config — the driver doesn't distribute the data.

        ❓ How things actually run — click to expand
        answers "where does my pipeline execute?"
      

      

        
Two independent runtimes coexist here.


        
1. SQL queries — you type SQL in the Playground or via
        POST /mesh/queries. The driver plans the query and
        splits it into partial-SQL tasks. Each task goes to one of the
        agent processes that hold the relevant partition (edge:
        partition:docs:us → agent-us). Rows stream back
        to the driver over NATS. This is the distributed part.


        
2. Pipelines — you submit a job spec via
        POST /mesh/jobs/run. In Phase 1 (right now) the
        driver's own JobRunner executes every node in-process. The
        agents are not involved. You'll see your pipeline show up in the
        big amber "Pipelines running in the driver JVM" panel below the driver
        box — that's where they live.


        
To distribute pipelines to agents (Phase 2) you need to:

        
    
          
  1. Install hitorro-mesh-agent-pipelines on an agent
              (adds the pipeline-node capability).
    2. 
          
  2. Set hitorro.mesh.pipelines.enabled=true in that agent's
              config.
    3. 
          
  3. Submit via POST /mesh/jobs/run-distributed instead of
              /run. The driver's PipelineScheduler
              then round-robins nodes across agents advertising the capability;
              they'll appear as pulsing pills inside the agent columns below.
    4. 
        


        
Persistent sinks (kvstore, lucene) write files under
        ~/.hitorro/pipelines/{kv,lucene}/<name>/. A subsequent
        job with source: {kind: kvstore, name: X} reads the same
        files back — that's how pipelines compose.
